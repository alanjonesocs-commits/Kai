# NIA15 Snapshot Integrity and Generation Specification

**Status:** Engineering specification for implementation and test review  
**Version:** 1.0.0  
**Applies to:** Android raw-memory snapshot producer and Debian 12 disposable retrieval index  
**Base:** PR #9 head `ce99deedca7d8fa1e94bb5b212ef0189d277a786`  
**Data class:** Synthetic fixtures only during implementation and CI

## 1. Purpose and safety boundary

This specification defines how NIA15 captures a consistent, verifiable snapshot of the canonical memory JSON and how the Debian retrieval index decides whether that snapshot may replace its active index.

The Pixel 9 memory store remains canonical. Snapshot creation is an explicit read operation. The Debian SQLite/FTS5 database is disposable and rebuildable. Debian MUST NOT write to Android memory, modify snapshot files, request automatic transfer, or treat its index as authoritative memory.

This work MUST NOT:
- invoke `MemoryStore.getAllMemories()`, migration callbacks, repair callbacks, or corruption-backup callbacks during raw snapshot capture;
- mutate canonical memory, migrate records, delete preferences, or repair malformed data;
- enable automatic export, transfer, synchronisation, or Debian write-back;
- infer that a snapshot is newer from its wall-clock timestamp, UUID, filename, filesystem time, or arrival order;
- use real personal memory in fixtures, CI, or reviewer test data.

A missing canonical setting is an error. A present value of `[]` is a valid, explicitly empty store and is not equivalent to a missing setting.

## 2. Threat model and guarantees

The design addresses accidental corruption, truncation, malformed input, record tampering, envelope-metadata tampering, replay/ordering ambiguity, duplicate identifiers, and unsafe index activation.

It does not establish the identity of the producer or protect against an attacker who can alter both a snapshot and its hashes. SHA-256 is an unkeyed digest: it detects changes relative to a trusted digest but is not a digital signature, MAC, proof of origin, or proof that the source device was uncompromised. Authenticity requires a separately designed key-management and signature system and is out of scope.

The indexer assumes the operator explicitly supplies the snapshot file. It must validate the entire envelope before touching the active index pointer.

## 3. Snapshot envelope

Schema 1.0.0 remains the compatibility baseline. The producer and consumer retain the existing fields:
- `format` = `nia-memory-snapshot`
- `schema_version` = `1.0.0`
- `snapshot_id`: non-empty opaque identifier
- `created_at_epoch_ms`: non-negative integer; descriptive timestamp only
- `source`: object with non-empty `system`; producer/device metadata
- `record_count`: exact number of records
- `hash_algorithm` = `SHA-256`
- `records_hash`: SHA-256 of canonical records array
- `records`: ordered array of memory-record JSON objects

Additive integrity fields:
- `hash_scope` = `snapshot-envelope-v1`
- `envelope_hash`: SHA-256 of the canonical envelope object after removing only `envelope_hash`.

Optional ordering field:
- `source_generation`: non-negative integer, only when emitted by a future explicitly approved monotonic generation authority. Omit it when no such authority exists. Do not substitute a timestamp, snapshot counter generated by the exporter, random ID, or Debian sequence.

Unknown top-level and record fields must be preserved by the raw Android producer and tolerated by forward-compatible consumers where the schema policy allows. Unknown fields are included in the envelope digest. A consumer MUST NOT discard unknown record fields when retaining the raw record.

## 4. Canonical JSON and digest algorithm

Both Kotlin and Python MUST implement the same byte-level rules.

1. Parse JSON as UTF-8. Reject invalid UTF-8, malformed JSON, duplicate object keys where the parser can detect them, non-finite numeric values, and unsupported root types.
2. Recursively sort object keys by Unicode code-point order. Arrays retain their original order.
3. Emit compact JSON: no insignificant whitespace; UTF-8 encoding; non-ASCII characters emitted directly (not escaped); JSON strings escaped according to the language-independent JSON rules; no NaN or Infinity.
4. Number representation MUST be cross-language deterministic. Schema-defined numeric fields are integers only. For arbitrary unknown numeric fields, implementations MUST preserve a normalised JSON number representation; if exact cross-language normalisation cannot be guaranteed, reject that numeric value rather than silently hash different bytes. Do not coerce strings to numbers.
5. Hash the canonical UTF-8 bytes with SHA-256 and encode as exactly 64 lowercase hexadecimal characters.

Digest definitions:
- `records_hash = SHA256(canonical_json(records))`.
- `envelope_hash = SHA256(canonical_json(envelope_without_envelope_hash))`, where only the `envelope_hash` property is removed. `records_hash`, `hash_scope`, `source_generation`, all metadata, and all records remain in the hashed object.

Validation order:
1. Validate structural envelope and field types.
2. Validate records and provenance.
3. Recompute and compare `records_hash`.
4. Recompute and compare `envelope_hash`.
5. Only then return a validated immutable input model to the indexing stage.

A mismatch is a hard rejection. No repair, re-hash-and-accept, or fallback to records-only validation is allowed for a schema version requiring envelope integrity. During migration, older schema-1.0.0 snapshots without the additive fields may be accepted only by an explicitly labelled legacy compatibility path; they MUST NOT be treated as envelope-verified and MUST NOT activate as a new trusted generation by default.

## 5. Record and provenance validation

For every record require the existing fields:
`key`, `content`, `createdAt`, `updatedAt`, `category`, `hitCount`, `source`, `id`, `receiptStatus`, `claimStatus`, `factStatus`, `resolutionStatus`, `sourceConversationId`, `provenance`.

Rules:
- `key`, `content`, and `id` are non-empty strings.
- IDs are unique within a snapshot. Duplicate keys are permitted because separate claims may share a key.
- `createdAt`, `updatedAt`, `hitCount`, and provenance `observedAt` are non-negative integers; booleans are not integers for validation purposes.
- Category and assessment values must be recognised enum values. Unknown future enum values are rejected until a compatible schema/version policy is introduced; they are not silently mapped.
- `source` and `sourceConversationId` may be null or strings, but their properties must be present.
- `provenance` must be an array. Every provenance item must be an object containing `source`, `conversationId`, and `observedAt`; the first two may be null or strings and the timestamp must be a non-negative integer.
- Missing properties, explicit null where not permitted, wrong types, blank required strings, invalid status values, duplicate IDs, or negative numeric values cause rejection.
- An empty provenance array is structurally valid only if product policy explicitly permits records without provenance; until that decision is made, the producer should reject records lacking at least one provenance item. The implementation must document which policy it enforces and test it consistently.

Unknown record properties are retained and hashed. Required known fields are never inferred from unknown fields.

## 6. Source-generation and index activation policy

A timestamp is not a generation counter. Clock skew, restored backups, clock resets, delayed transfer, and manually supplied files make timestamp ordering unreliable.

Generation states:
- **Same envelope hash:** idempotent; return `ALREADY_INDEXED` when snapshot identity also matches, or `IDENTICAL_CONTENT` only when the complete integrity-relevant envelope digest matches.
- **Same snapshot_id, different envelope hash:** reject as an identity collision or altered snapshot.
- **Different envelope hash, no source_generation:** return `NEEDS_VERIFICATION`; leave active index unchanged.
- **Different envelope hash, source_generation present on both snapshots and same declared authority:** accept only if incoming generation is strictly greater. Equal or lower values reject.
- **Generation missing on either side, authority differs, malformed, or discontinuous under a future authority policy:** `NEEDS_VERIFICATION`; no activation.
- **No active index:** a valid explicitly supplied snapshot may initialise the disposable index. This does not prove it is the newest canonical state.

For this phase, Android does not emit a trusted monotonic `source_generation`. Therefore changed content after initial indexing must not replace the active index automatically. Do not expose a generic `--accept-uncertain-order` bypass in unattended execution. If an operator-controlled one-off rebuild is ever required, it must be a separate explicit rebuild operation with a conspicuous audit record and no claim that the input is newer.

A content hash identifies content; it does not order content. A timestamp describes when the exporter says it created the snapshot; it does not prove freshness.

## 7. Index construction and activation

- Validate the complete snapshot before creating a generation directory.
- Build into a new temporary directory on the same filesystem as the generation store.
- Use SQLite integrity checks and fsync the database and containing directories before activation.
- Atomically rename the completed generation directory, then atomically replace `CURRENT`.
- Never delete or modify the previous active generation as part of a failed build.
- On any failure before pointer replacement, the old `CURRENT` remains authoritative.
- After activation, read back and validate the pointer and index metadata.
- Store the snapshot envelope hash, records hash, schema version, snapshot ID, source generation (if any), and source metadata in index metadata.
- Index records retain the original raw JSON, including unknown fields.
- The index remains disposable; rebuild must be possible from the supplied snapshot without consulting or mutating Android.

## 8. Error model and audit output

Use explicit outcomes:
- `ACCEPTED_FOR_INDEX`: structurally and cryptographically self-consistent; may initialise an empty index or proceed under generation rules.
- `ALREADY_INDEXED`: exact same snapshot/envelope already active.
- `IDENTICAL_CONTENT`: exact same integrity-relevant envelope digest already active under a different delivery event.
- `NEEDS_VERIFICATION`: valid input but freshness/order cannot be established; active index unchanged.
- `REJECTED`: invalid structure, schema, digest, record, identity, or generation regression; active index unchanged.

Audit output should include decision, snapshot ID, schema version, envelope hash, records hash, source generation (or explicit null), reason, and active generation before/after. Do not include memory content in routine logs. Never log secrets or raw personal records.

## 9. Required test matrix

Kotlin producer and Python consumer must share checked-in synthetic fixtures and agree on both digests.

Integrity:
- canonical object-key ordering and compact UTF-8 bytes;
- Unicode and escaped-string fixture;
- records hash detects record tampering;
- envelope hash detects changes to snapshot ID, timestamp, source metadata, record count, hash scope, generation, records hash, and records;
- malformed/missing/uppercase/incorrect-length digest rejected;
- metadata tampering with unchanged records rejected;
- duplicate JSON keys rejected where parser support exists.

Storage and validation:
- missing settings value rejected;
- stored empty array accepted and hashed;
- blank/malformed/non-array raw JSON rejected;
- null/missing required fields rejected;
- wrong numeric types, booleans, negative numbers rejected;
- invalid category/status rejected;
- malformed provenance, null/type errors and blank provenance strings handled according to the chosen policy;
- duplicate IDs rejected; duplicate keys with distinct IDs retained;
- unknown future record fields survive Android snapshot and Python index round-trip.

Generation and activation:
- first valid snapshot initialises empty disposable index;
- exact same snapshot is idempotent;
- same snapshot ID with changed envelope is rejected;
- changed content without source generation returns NEEDS_VERIFICATION and does not move CURRENT;
- strictly increasing generation from same authority may activate;
- equal/lower generation rejects;
- generation absent on one side returns NEEDS_VERIFICATION;
- timestamp newer/older does not override missing generation;
- interrupted build and failed SQLite integrity check leave CURRENT unchanged;
- index metadata records the validated envelope hash.

## 10. Implementation gates and evidence

Implementation is complete only when:
- Kotlin and Python produce identical canonical digest results for the same fixture;
- all tests above pass in CI;
- PR diff is reviewed for unintended changes to canonical storage or startup recovery;
- CI output is linked to the exact commit SHA;
- no real-memory or Pixel runtime claim is made without separate device evidence.

CI passing establishes only the tested host/synthetic behaviour. It does not establish Android encrypted-preferences internals, Pixel 9 runtime behaviour, successful real-memory export, or real retrieval.

## 11. Forensic review findings against the pre-existing implementation

Findings requiring remediation:
1. Existing `records_hash` omits envelope metadata; metadata tampering is undetected.
2. Python `accept_uncertain_order` allows changed content to bypass missing-generation uncertainty.
3. Existing index metadata and idempotency decisions are based on records hash, not complete envelope integrity.
4. Kotlin raw validation checks provenance field presence and non-negative timestamps but does not explicitly reject blank non-null provenance strings.
5. Existing test coverage lacks envelope metadata tampering, cross-language envelope digest, and generation non-activation assertions for timestamp-only differences.
6. Existing comments describe preservation as byte-semantic, although canonicalisation changes whitespace and object key order; the accurate guarantee is semantic JSON-value preservation for retained fields.

Positive controls to retain:
- raw Android snapshot path reads nullable raw settings value rather than the migration/repair read path;
- missing store is distinguished from stored empty array;
- malformed and incomplete input fails closed;
- unknown record fields are retained;
- Debian index is a separate rebuildable database with atomic pointer activation.

## 12. Approval and compatibility

This specification does not authorise transfer of real memory, Pixel storage writes, automatic synchronisation, Debian write-back, or merging PR #8/#9. Implementation must be isolated on a child branch from the current PR #9 head. Any change to canonical storage, migration semantics, export scheduling, generation authority, signing/key management, or merge state requires separate approval.

Schema compatibility must be explicit. Do not silently label an old records-only snapshot as envelope-verified. A future schema version may make envelope integrity mandatory; until then, legacy compatibility must be clearly marked and fail closed for activation where freshness or integrity scope is insufficient.


## 13. Binding implementation decisions — contract lock 1.1.0

**Decision status:** Approved for synthetic implementation on the forensic branch only. This section supersedes conflicting compatibility wording in Sections 3, 4, 6 and 12 above.

### 13.1 Schema version

The coordinated producer/consumer contract is **schema_version 1.1.0**. The JSON Schema file must be versioned as `nia-memory-snapshot-1.1.schema.json`. Schema 1.0.0 is legacy records-hash-only input and is not eligible to initialise or replace the trusted active index through the normal `index` command. No silent upgrade or automatic re-hashing of legacy snapshots is permitted.

### 13.2 Mandatory envelope fields

Schema 1.1.0 requires all existing envelope fields plus:
- `hash_scope`: exactly `snapshot-envelope-v1`;
- `envelope_hash`: exactly 64 lowercase hexadecimal characters.

`source_generation` remains optional. Schema 1.1.0 does not imply that a generation authority exists. The producer MUST omit `source_generation` until an explicitly approved canonical monotonic generation authority is implemented. A generation value without a stable `generation_authority` identifier is invalid for ordering and MUST NOT be used to activate changed content.

### 13.3 Numeric and parser interoperability

To avoid Kotlin/Python disagreement, schema 1.1.0 canonical JSON accepts only integer JSON numbers. Any decimal/exponent-form number anywhere in the envelope, including an unknown future property, is rejected. Booleans remain distinct from integers. Implementations MUST reject duplicate object member names before converting JSON into map/object structures; if the selected parser cannot reliably detect duplicates, an explicit duplicate-key scan/parser layer is required before normal decoding.

Object keys are ordered by Unicode code-point order; arrays retain order. Strings use JSON escaping and UTF-8 output with non-ASCII characters emitted directly. Canonical bytes are compact with no insignificant whitespace. Both digest calculations use these exact bytes.

### 13.4 Provenance policy

Every record MUST contain at least one provenance item for schema 1.1.0. Each provenance item must contain all three required properties. Non-null `source` and `conversationId` values must be non-blank strings; null remains permitted. `observedAt` must be a non-negative integer. Record-level `source` and `sourceConversationId` remain nullable but required properties.

### 13.5 Activation policy

For this implementation phase no trusted generation authority is present. Therefore, after the first valid schema 1.1.0 snapshot initialises an empty index, any different envelope hash MUST return `NEEDS_VERIFICATION` and MUST leave `CURRENT` unchanged. Timestamp, UUID, filename, delivery order and operator flags MUST NOT override this rule. The normal CLI MUST NOT expose an uncertain-order bypass. Exact envelope-hash equality is idempotent; same snapshot ID with a different envelope hash is rejected.

### 13.6 Required metadata and test lock

The active SQLite metadata MUST store `schema_version`, `snapshot_id`, `records_hash`, `envelope_hash`, `hash_scope`, `created_at_epoch_ms`, `record_count`, `source_system`, and nullable `source_generation` / `generation_authority` values. Audit and status output must not contain record content.

The shared golden fixture is synthetic and must include Unicode, nested unknown object fields, arrays, escaped characters and integer boundary values. Kotlin and Python must assert the same records hash AND envelope hash. Tests must prove that altering any integrity-covered envelope metadata fails validation, and that a changed valid snapshot without generation leaves the active `CURRENT` pointer unchanged.

This contract lock is not evidence of implementation or test completion. No device, real-memory or merge authorisation is implied.
